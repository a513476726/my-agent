# ADR-0001：数据库选用 PostgreSQL 16

- **状态**：已接受
- **日期**：2026-10-24
- **决策者**：项目负责人

## 背景

平台需要持久化项目登记、文档元信息、知识库映射、报告正文与条目、能力沉淀、任务定义与运行记录、会话与审计。数据量级很小（千级文档、万级消息），因此**性能不是选型依据**，能力边界与长期可维护性才是。

团队既有技术栈以 RuoYi + MySQL 为主，MySQL 的运维熟悉度更高，这是本决策必须正面权衡的反对意见。

## 决策

采用 **PostgreSQL 16**。

## 理由（按对本项目的权重排序）

1. **JSONB + GIN 索引**：`messages.citations`、`knowledge_bases.config`、`jobs.config` 形状不固定且需要按路径查询。MySQL 需借助生成列或多值索引，写法绕且易漏。
2. **事务性 DDL**：迁移可持续演进，失败可干净回滚。MySQL 的 DDL 隐式提交，失败会留下半截状态。
3. **部分索引**：需要「只索引未完成任务」「只索引失败运行」，MySQL 不支持。
4. **原生数组**：`capability_notes.tags` 直接以数组存储与查询。
5. **向量路径**：若未来把检索从 RAGFlow 收回自建库，`pgvector` 是成熟选择。
6. **许可**：PostgreSQL License 宽松；MySQL 为 GPLv2 + Oracle 双授权，内部使用无实际风险但存在治理不确定性。

## 替代方案与未采纳原因

**MySQL 8** —— 能力上可覆盖约 80%：

- `FOR UPDATE SKIP LOCKED`、CTE、窗口函数均支持，任务抢锁与报表聚合无差异。
- 不采纳的决定性差异只有三条：事务性 DDL、JSONB 查询体验、部分索引。
- 若未来出现以下情况，应重新评估本决策：运维长期由单一人员承担且其 MySQL 排障能力明显更强；公司已有成熟 MySQL 高可用与备份体系可零成本接入；团队接手者普遍只熟悉 MySQL。

## 后果

**正面**
- 半结构化数据查询与迁移安全性更好。
- 为未来的向量检索保留路径。

**负面**
- 团队熟悉度低于 MySQL，故障排查的学习成本更高。
- 小规格服务器需自行调优 `shared_buffers`、`work_mem`；高连接数场景需引入 PgBouncer。
- 国内云厂商的默认推荐与故障案例以 MySQL 居多。

## 补充约束

RAGFlow 的编排中自带 `mysql:8.0.40`，那是知识库服务的内部元数据库。**不得与本平台的数据库共用实例**——共用会把两个服务的升级、备份与故障域绑定，违背「知识库分离」的设计目标。
